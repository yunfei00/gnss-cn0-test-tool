# 01 产品需求与范围

## 1. 目标

构建可独立完成闭环的 Windows GNSS C/N0 测试系统。测试对象为具有 GNSS 接收器的 Android 手机；PC 经 ADB 控制业务场景及采集端，以一个测试计划执行多个 APP/设备业务场景，并比较 GPS L1 与 L5 的 C/N0。

**测试核心是业务场景造成的接收差异**，而非控制 GSS7000。MVP 可以使用真实卫星；GSS7000 只是未来可控信号源。

## 2. 角色与平台

- 操作员：配置设备、选择场景、开始任务、在半自动场景人工操作与确认、查看报告。
- Windows PC：负责唯一调度、状态保存、时间窗口管理、分析、导出和诊断。
- Android GnssLoggerApp：持续采集及记录测试边界。
- Android AutoTestSceneApp：执行已有内置场景；外部 APP 可独立接入自动适配器或人工操作。
- 不要求手机 root；Android 应用定位/后台权限应由用户正常授予。

## 3. 必须实现

## 4. 自动与半自动统一流程

输入一次完整计划，每场景定义：`scene_id`、`mode=auto|manual`、启动参数、稳定等待、有效采样时间、重复次数、失败策略。建议首轮：空闲基准、视频自动、游戏高负载自动、第三方导航半自动。

1. GNSS Logger 开始持续采集；预热完成。
2. 自动场景：启动并**确认场景实际 READY**；手动场景：显示指引，等待人工点击“已进入场景”。
3. 进入 STABILIZING，等待固定时长（可选配采样稳定判据）；此时 GNSS 原始记录仍连续产生。
4. Logger 写 MEASUREMENT_START 事件；PC 计时目标采样持续时间；Logger 写 END；获取事件回执。
5. 自动场景 STOP 并验证资源释放；手动场景提示人工退出并确认，或按计划保留至下一个场景。
6. 任务结束，提取日志并按 START/END 手机单调时间窗口分割，执行分析。

必须允许用户对某场景强制改为半自动；不支持的自动场景不可强行标记为自动成功。

## 5. 建议非功能指标（须真机校准）

- 默认采样 60s、稳定等待 20s、GNSS Logger 1s 定位请求（Status 实际回调率由硬件决定）。
- 性能与精度不得基于假定回调频率；窗口内零样本、不足覆盖、空频率都要明确显示。
- 任务可恢复的是**结果与元数据**；手机重启或会话失效的当前场景标记中断，不能无声续接。
- 完整、不可篡改来源的原始日志与事件文件，以 SHA-256 摘要保留。
- GNSS/位置敏感日志只本地保存，默认 .gitignore。

## 6. MVP 不做

- 直接控制 GSS7000 的专有 API/射频脚本；
- 自动适配所有第三方 APP 的 UI；
- 必须达到毫秒级跨设备同步；
- 初版实时逐卫星数据推送（先读取已完成 CSV，后续可升级）；
- 多手机并发、远程服务器、云端分析与定位轨迹可视化。

## 7. 决策与待验证

- GnssLoggerApp 现存内部目录导出权限、控制接口与 scene_name 实际存在差异，应先修复并验证；
- 场景 APP 的 STOP 和状态回读必须按真实 Activity 验证；
- L5 可用性依赖实际手机/固件，缺少 L5 不能伪造测试结论；
- 真正测量干扰影响时，应优先控制温度、姿态、卫星可见性、屏幕亮度、网络状态，并穿插基准 A-B-A。
